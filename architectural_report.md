# Informe de Arquitectura del Proyecto Red Level Circle

## 1. Introducción

Este informe detalla la arquitectura del proyecto `red-level-circle`, con el objetivo de proporcionar una comprensión exhaustiva de su estructura, tecnologías y flujos de datos. Este análisis servirá como base para futuras actualizaciones y modificaciones, asegurando la integridad y funcionalidad del sistema.

## 2. Estructura General del Proyecto

El proyecto `red-level-circle` sigue una arquitectura de monorepo, dividiendo claramente el frontend (`client/`) y el backend (`server/`), además de compartir código (`shared/`) y configuraciones de base de datos (`drizzle/`).

```
red-level-circle/
├── client/             # Aplicación frontend (React, Vite)
│   ├── public/         # Archivos estáticos
│   ├── src/            # Código fuente del frontend
│   │   ├── _core/      # Hooks y utilidades principales
│   │   ├── components/ # Componentes reutilizables de UI
│   │   ├── contexts/   # Contextos de React
│   │   ├── hooks/      # Hooks personalizados
│   │   ├── lib/        # Librerías y configuraciones (e.g., tRPC)
│   │   ├── pages/      # Páginas de la aplicación
│   │   └── ...
├── drizzle/            # Configuraciones y esquemas de la base de datos (Drizzle ORM)
│   ├── migrations/     # Migraciones de la base de datos
│   ├── schema.ts       # Definición del esquema de la base de datos
│   ├── relations.ts    # Definición de relaciones entre tablas
│   └── ...
├── patches/            # Parches para dependencias
├── scripts/            # Scripts de utilidad
├── server/             # Aplicación backend (Express.js, tRPC)
│   ├── _core/          # Lógica central del servidor (autenticación, tRPC, env)
│   ├── db.ts           # Capa de acceso a datos (Drizzle ORM)
│   ├── routers.ts      # Definición de rutas y procedimientos tRPC
│   ├── jobs/           # Tareas programadas (e.g., sincronización de Twitch)
│   └── ...
├── shared/             # Código compartido entre frontend y backend
│   ├── _core/          # Utilidades compartidas (e.g., errores)
│   ├── const.ts        # Constantes compartidas
│   └── types.ts        # Definiciones de tipos compartidas
├── package.json        # Dependencias y scripts del proyecto
├── tsconfig.json       # Configuración de TypeScript
├── vite.config.ts      # Configuración de Vite
└── ...
```

                                                                                                                                                                                                                                                                                   Toda la información del proyecto se ha analizado y se ha creado un resumen estructurado con los siguientes puntos clave:  **Arquitectura General del Proyecto**  El proyecto `red-level-circle` es una aplicación web completa con una arquitectura de monorepo, utilizando TypeScript en todo el stack. Se compone principalmente de un cliente (frontend), un servidor (backend) y una capa de base de datos/ORM, con utilidades y tipos compartidos.  **Estructura de Carpetas**  *   **`client/`**: Contiene la aplicación frontend.  *   `client/public/`: Archivos estáticos como imágenes y assets.  *   `client/src/`: Código fuente de React.  *   `client/src/_core/`: Hooks y utilidades centrales del cliente.  *   `client/src/components/`: Componentes reutilizables de la interfaz de usuario.  *   `client/src/contexts/`: Contextos de React para el manejo de estado global.  *   `client/src/hooks/`: Hooks personalizados.  *   `client/src/lib/`: Configuraciones y clientes de librerías (e.g., tRPC).  *   `client/src/pages/`: Componentes que representan las diferentes vistas o páginas de la aplicación.  *   **`drizzle/`**: Gestiona la configuración y el esquema de la base de datos.  *   `drizzle/migrations/`: Archivos de migración generados por Drizzle Kit.  *   `drizzle/schema.ts`: Define las tablas, columnas y tipos de datos de la base de datos utilizando Drizzle ORM.  *   `drizzle/relations.ts`: Define las relaciones entre las tablas del esquema.  *   **`server/`**: Contiene la aplicación backend.  *   `server/_core/`: Lógica central del servidor, incluyendo configuración de Express, tRPC, manejo de entorno y autenticación OAuth.  *   `server/db.ts`: Capa de abstracción para interactuar con la base de datos a través de Drizzle ORM, conteniendo todas las funciones CRUD y consultas complejas.  *   `server/routers.ts`: Define los procedimientos y rutas de la API tRPC, organizados por dominios (auth, tournaments, teams, etc.).  *   `server/jobs/`: Contiene tareas programadas como la sincronización de Twitch y el cierre de apuestas.  *   **`shared/`**: Contiene código y tipos que son utilizados tanto por el cliente como por el servidor para asegurar consistencia.  *   `shared/_core/`: Utilidades compartidas, como manejo de errores.  *   `shared/const.ts`: Constantes globales.  *   `shared/types.ts`: Definiciones de tipos comunes.  *   **Archivos de configuración raíz**: `package.json`, `tsconfig.json`, `vite.config.ts`, `drizzle.config.ts`, `pnpm-lock.yaml`.  **Flujo Frontend → Backend → Database**  1.  **Frontend (React/Vite)**: La interfaz de usuario, construida con React y Vite, interactúa con el backend a través de llamadas tRPC. Las rutas del frontend se gestionan con `wouter`.  2.  **Llamadas tRPC**: El cliente tRPC en el frontend (`client/src/lib/trpc.ts`) realiza llamadas a los procedimientos definidos en el `appRouter` del backend (`server/routers.ts`).  3.  **Backend (Express.js/tRPC)**:  *   El servidor Express.js (`server/_core/index.ts`) actúa como punto de entrada.  *   Las solicitudes tRPC son manejadas por `createExpressMiddleware`, que utiliza `createContext` (`server/_core/context.ts`) para establecer el contexto de la solicitud, incluyendo la autenticación del usuario.  *   El `appRouter` (`server/routers.ts`) define los endpoints de la API. Los procedimientos pueden ser `publicProcedure` (accesible sin autenticación), `protectedProcedure` (requiere autenticación), `premiumProcedure` (requiere rol 'premium' o 'admin'), `creatorProcedure` (requiere rol 'content_creator' aprobado) o `adminProcedure` (requiere rol 'admin').  *   La lógica de negocio dentro de estos procedimientos interactúa con la capa de acceso a datos.  4.  **Capa de Acceso a Datos (Drizzle ORM)**:  *   `server/db.ts` contiene funciones que encapsulan las operaciones de base de datos utilizando Drizzle ORM. Estas funciones interactúan directamente con el esquema definido en `drizzle/schema.ts`.  *   Las operaciones incluyen `upsertUser`, `createTeam`, `getTournaments`, `updateMatchResult`, etc.  5.  **Base de Datos (MySQL)**: Drizzle ORM se conecta a una base de datos MySQL (o compatible) utilizando `mysql2`. El esquema de la base de datos se define en `drizzle/schema.ts` y las migraciones se gestionan con `drizzle-kit`.  **Componentes Principales del Frontend**  *   **`SidebarLayout`**: Componente de layout principal que envuelve la aplicación, proporcionando una barra lateral de navegación.  *   **`OnboardingModal`**: Modal para guiar a nuevos usuarios a completar su perfil.  *   **`RosterCard`**: Tarjeta de visualización de jugadores con información detallada, estadísticas y roles. Utiliza `RosterCard.css` para estilos específicos.  *   **`HighlightCard`**: Tarjetas utilizadas en la página de Ranking para mostrar equipos destacados (campeón, mejor tasa de victorias, etc.).  *   **`TeamSidePanel`**: Panel lateral deslizante que muestra información detallada de un equipo al seleccionarlo en la tabla de ranking.  *   **`BracketView`**: Componente para visualizar los brackets de torneos (eliminación simple, doble eliminación).  *   **`ui/`**: Directorio que contiene componentes de UI genéricos, probablemente basados en `shadcn/ui` y `Radix UI`, estilizados con Tailwind CSS.  **APIs Disponibles**  La API se construye con tRPC, lo que permite un tipado de extremo a extremo. Los routers principales son:

*   **`auth`**: Maneja la autenticación de usuarios, perfiles (`me`, `updateProfile`, `profile`), y la billetera (`wallet`).  *   **`tournaments`**: Gestión de torneos (`list`, `byId`, `create`, `update`, `registrations`, `matches`, `generateBracket`, etc.).  *   **`teams`**: Gestión de equipos (`list`, `byId`, `create`, `members`, `join`, `leave`, `achievements`, etc.).  *   **`ranking`**: Obtención de datos para el ranking de equipos y jugadores.  *   **`news`**: Gestión de artículos de noticias (`list`, `byId`, `create`, `update`, `delete`).  *   **`streams`**: Gestión de transmisiones en vivo (`list`, `create`, `stop`).  *   **`bets`**: Gestión de apuestas en partidos de torneos.  *   **`shop`**: Gestión de ítems de la tienda y compras.  *   **`cosmetics`**: Gestión de cosméticos para usuarios.  *   **`rewards`**: Gestión de tareas de recompensa y reclamos.  *   **`ads`**: Gestión de anuncios de marca.  *   **`community`**: Funcionalidades de seguimiento de usuarios.  *   **`admin`**: Procedimientos protegidos para administradores (gestión de usuarios, torneos, ítems de tienda, etc.).  **Modelos de Base de Datos**  El esquema de la base de datos (`drizzle/schema.ts`) define las siguientes tablas principales:

*   **`users`**: Información de usuarios (ID, `openId`, nombre, email, método de login, rol, tipo de perfil, avatar, biografía, nickname, juego principal, rol en juego, ELO, región competitiva, `gameId`, `competitiveScore`, país, redes sociales, `bannerUrl`, `rosterPhoto`, `rosterImageUrl`, `isVerified`, `rlcBalance`, `createdAt`, `updatedAt`, `lastSignedIn`).  *   **`teams`**: Información de equipos (ID, nombre, tag, logo, banner, `captainId`, descripción, juego, `gameSlug`, país, puntos, victorias, derrotas, torneos jugados/ganados, redes sociales, `isVerified`, `createdAt`, `updatedAt`).  *   **`teamMembers`**: Relación entre usuarios y equipos (ID, `teamId`, `userId`, rol, `gameId`, `joinedAt`).  *   **`teamAchievements`**: Logros de equipos (ID, `teamId`, título, descripción, `tournamentId`, `awardedAt`).  *   **`tournaments`**: Información de torneos (ID, nombre, juego, `gameSlug`, descripción, reglas, `bracketType`, `registrationType`, `maxTeams`, `minPlayersPerTeam`, `maxPlayersPerTeam`, premios, fechas de registro/inicio/fin, estado, `adminNote`, `creatorId`, `winnerId`, banner, colores, `streamUrl`, `streamPlatform`, `isLive`, `viewCount`, `createdAt`, `updatedAt`).  *   **`tournamentRegistrations`**: Registros de equipos/jugadores en torneos (ID, `tournamentId`, `teamId`, estado, mensajes, fechas).  *   **`registrationAuditLog`**: Historial de cambios de estado en registros de torneos.  *   **`tournamentMatches`**: Partidos dentro de un torneo (ID, `tournamentId`, ronda, número de partido, `team1Id`, `team2Id`, `winnerId`, scores, estado, fechas programadas/cierre de apuestas/completado, notas, `bracketPosition`).  *   **`news`**: Artículos de noticias (ID, título, slug, extracto, contenido, imagen de portada, categoría, `authorId`, `isPublished`, `isFeatured`, `viewCount`, `publishedAt`, `createdAt`, `updatedAt`).  *   **`rlcTransactions`**: Transacciones de la moneda virtual RLC.  *   **`games`**: Juegos soportados por la plataforma.  *   **`bets`**: Apuestas realizadas por los usuarios.  *   **`streams`**: Transmisiones en vivo.  *   **`promotions`**: Promociones activas.  *   **`shopItems`**: Ítems disponibles en la tienda.  *   **`shopOrders`**: Órdenes de compra de ítems de la tienda.  *   **`cosmetics`**: Cosméticos para usuarios.  *   **`userCosmetics`**: Cosméticos que posee un usuario.  *   **`rewardTasks`**: Tareas de recompensa.  *   **`userRewardClaims`**: Reclamos de recompensas por usuarios.  *   **`brandAds`**: Anuncios de marca.  *   **`userFollows`**: Relaciones de seguimiento entre usuarios.  *   **`contentCreators`**: Información de creadores de contenido.  *   **`verificationRequests`**: Solicitudes de verificación.  **Sistema de Autenticación**  El sistema de autenticación se basa en un servicio OAuth externo (`server/_core/sdk.ts`) y utiliza JWTs (JSON Web Tokens) para la gestión de sesiones.  *   Los usuarios se autentican a través de un flujo OAuth, obteniendo un token de acceso.  *   Este token se intercambia por información del usuario y se utiliza para crear una sesión interna, almacenada en una cookie firmada con JWT.  *   El middleware `createContext` (`server/_core/context.ts`) verifica la cookie de sesión en cada solicitud para autenticar al usuario y adjuntar su información al contexto de tRPC.  *   Si el usuario no existe en la base de datos local, se sincroniza automáticamente desde el servicio OAuth.  **Sistema de Estilos**  El proyecto utiliza **Tailwind CSS** para la mayoría de sus estilos, complementado con **Radix UI** para componentes accesibles y sin estilo, y **`shadcn/ui`** para componentes de UI pre-construidos y estilizados con Tailwind.  *   Los estilos globales se definen en `client/src/index.css`, que importa Tailwind y `tw-animate-css`.  *   Se utilizan variables CSS personalizadas (`--bg-main`, `--accent-red`, etc.) para definir un sistema de diseño temático, inspirado en la paleta de Epic Games Store.  *   Las fuentes principales son 'Inter' para el cuerpo del texto y 'Orbitron' para títulos, manteniendo una identidad de marca distintiva.  **Lógica de Negocio**  La lógica de negocio está distribuida principalmente en el archivo `server/db.ts` (para operaciones de base de datos complejas) y en los procedimientos tRPC definidos en `server/routers.ts`. Ejemplos incluyen la creación de torneos, gestión de registros, resolución de apuestas, sincronización de transmisiones de Twitch, etc.  ## 4. Posibles Puntos de Mejora

1.  **Separación de Responsabilidades en `server/db.ts`**: El archivo `server/db.ts` es muy extenso (más de 3000 líneas), lo que dificulta su mantenimiento y escalabilidad. Se podría refactorizar en módulos más pequeños, agrupando las funciones por entidad (e.g., `db/users.ts`, `db/tournaments.ts`).  2.  **Manejo de Errores Centralizado**: Aunque tRPC maneja errores, una estrategia más granular para la gestión de errores a nivel de aplicación (logging, reporting, custom error types) podría mejorar la robustez.  3.  **Optimización de Consultas de Base de Datos**: Con un archivo `db.ts` tan grande, es posible que algunas consultas no estén completamente optimizadas. Una revisión periódica y el uso de herramientas de monitoreo de rendimiento de la base de datos serían beneficiosos.  4.  **Internacionalización (i18n)**: Actualmente, los textos parecen estar en español. Si se planea expandir a otros idiomas, se necesitaría una solución de i18n completa.  5.  **Pruebas Unitarias y de Integración**: Aunque `vitest` está configurado, asegurar una cobertura de pruebas adecuada, especialmente en la lógica de negocio crítica, es fundamental.  ## 5. Riesgos al Modificar el Código

1.  **Impacto en la Base de Datos**: Cualquier cambio en `drizzle/schema.ts` o en las funciones de `server/db.ts` puede tener un impacto significativo en la integridad de los datos y en la compatibilidad con versiones anteriores. Las migraciones deben ser manejadas con extremo cuidado.  2.  **Coherencia de la API tRPC**: Modificar los procedimientos tRPC en `server/routers.ts` sin actualizar el cliente (`client/src/lib/trpc.ts`) resultará en errores de tipado y de tiempo de ejecución. El tipado de extremo a extremo de tRPC ayuda a mitigar esto, pero requiere atención.  3.  **Efectos Secundarios en Componentes de UI**: Los cambios en componentes de UI compartidos o en el sistema de estilos (Tailwind, Radix UI) pueden afectar inesperadamente a múltiples partes del frontend.  4.  **Lógica de Negocio Compleja**: La lógica de negocio relacionada con torneos, apuestas y transacciones de RLC es compleja. Las modificaciones en estas áreas requieren una comprensión profunda para evitar introducir errores que afecten la funcionalidad central de la plataforma.  5.  **Dependencias Externas**: Actualizar dependencias en `package.json` puede introducir cambios de última hora o incompatibilidades, especialmente con librerías como React, Vite o Drizzle.
